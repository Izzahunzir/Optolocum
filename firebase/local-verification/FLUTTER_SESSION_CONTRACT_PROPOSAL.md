# Proposed trusted session validation (not implemented)

Real-backend sign-in and post-enrollment access fail closed until a separately reviewed server endpoint exists. This proposal does not activate or implement an endpoint. Keep `account_access` unreadable to clients.

Proposed request: `POST /api/session/validate`, HTTPS only, no redirects, `Authorization: Bearer <Firebase ID token>`, `Content-Type: application/json`, exact body `{ "accountType": "locum" }` or `{ "accountType": "practice_owner" }`. Do not accept a UID, access state, cutoff, or role from the client.

The server must verify the ID token with revocation checking, load the current Firebase Auth user, reject disabled users and admin accounts, load the trusted assignment and `account_access/{uid}` from the server, validate the complete access schema, require active access and no operation in progress, require integer `auth_time > validAfter`, and compare the assignment to the requested type. Reject missing, malformed, inactive, stale or mismatched records. Use no cached access decisions. Check authorization again for each protected operation; this endpoint is not a substitute for Firestore rules or server-side checks.

Proposed successful response: HTTP 200, `{ "data": { "uid": "<verified UID>", "accountType": "locum", "access": "active" } }`; the client must check all three values and the current Firebase UID. Return 401 for invalid, expired or revoked authentication; 403 for disabled, mismatched or unavailable access; 503 for unavailable validation. Return no access record, cutoff, token, sensitive fields or internal error details. Send `Cache-Control: no-store`. Do not distinguish missing account records in public error messages. HTTPS origin, native-client, abuse-control and TLS policies remain subject to server review.

The application must only navigate after a successful validated response, clear enrollment recovery only after identity and access are confirmed, sign out on failures, and handle later token revocation and account changes on every sensitive request. This application currently intentionally cannot authorize real-mode login or finish post-enrollment navigation.

Before activation, the Admin repository's applicant draft/upload/finalize logic must atomically prohibit new verification revisions for an approved account, including approvals racing with finalization; allow rejected accounts to create a fresh revision, and retain old revisions and reviews. Existing submitted-request recovery must remain idempotent. The reviewed Firestore candidate must prohibit client changes to approved verification fields and approval status and preserve approved-only job creation/application checks. Admin SDK code bypasses Firestore rules, so both controls are necessary. The current local candidate and isolated finalizer are not deployed and do not secure the real backend. Review current deployed rules and test all paths before any separately authorized activation.
